# 1. PROJECT VISION

Hamlet is a persistent medieval village inhabited by autonomous AI-driven characters.

The inhabitants are not ordinary scripted NPCs. Each character has an identity and background, personality and values, needs and preferences, ambitions, goals, plans, memories, relationships, knowledge, beliefs, occupation, and daily routines. They can initiate conversations, react to events, develop ambitions, and change behavior.

The village must evolve over time through friendships, rivalries, businesses, traditions, rumors, economic relationships, community projects, and unexpected social situations.

The player primarily observes and interacts with the simulation rather than directly controlling every character. The world persists between application sessions.

**Core design principle:** The simulation owns the world. AI owns character decision-making. AI proposes decisions; the simulation validates and executes them. AI must never directly modify authoritative world state.

# 14. AI ACTION RESPONSE FORMAT

All NPC decision requests return structured JSON. Use Kotlin serialization and strict schemas.

Example:

{
  "npc_id": "thomas",
  "decision_type": "goal_action",
  "reasoning_summary": "I need to acquire flour for my household.",
  "goal": {
    "description": "Acquire flour",
    "priority": 75
  },
  "action": {
    "type": "travel_to",
    "target_id": "market",
    "parameters": {}
  },
  "expected_outcome": "Reach the market",
  "memory_candidates": [
    {
      "content": "I need to purchase flour.",
      "importance": 40
    }
  ]
}

Use brief reasoning summaries only. Do not request or store hidden chain-of-thought.

Validate every field before the action reaches the simulation. If JSON is malformed, retry or use fallback behavior. A failed AI response must never corrupt the world.

# 16. MEMORY SYSTEM

Build persistent individual memories.

Categories:
1. Episodic: events personally experienced.
2. Semantic: facts and knowledge.
3. Social: knowledge about people and relationships.
4. Procedural: skills and learned methods.
5. Autobiographical: personal history and identity.

Each memory stores ID, owner NPC, event ID if applicable, category, content, importance, emotional weight, confidence, creation time, and last accessed time.

Use SQLite FTS5 initially. Keep a replaceable MemorySearch interface for future semantic or vector retrieval.

Implement memory consolidation. Important experiences should be retained more strongly than routine events.

Memory privacy is essential: an NPC cannot automatically access another NPC's private memories. Rumors are stored as information received from another source, not automatically treated as verified truth.

# 19. OFFLINE OPERATION

Offline functionality is mandatory. The simulation must remain meaningful without internet.

When offline:
- World clock advances when execution is permitted.
- NPC schedules operate locally.
- Needs change.
- NPCs move using local rules.
- Existing plans continue.
- Local events are generated.
- AI requests are queued or skipped safely.
- Deterministic fallback decisions are used.

When the application reopens:
- Calculate elapsed time using persisted timestamps.
- Advance deterministic simulation systems.
- Resolve eligible offline events.
- Revalidate queued AI actions.
- Resume active simulation.

Never blindly execute stale queued decisions.

Account for Android lifecycle and battery restrictions. Do not promise continuous background simulation when Android has suspended the application. Use WorkManager for deferred work. Use a foreground service only when appropriate, permitted, and clearly enabled by the user.

# 21. SIMULATION SCHEDULER

Build a central scheduler. Do not run 12 permanent AI loops. Use event-driven scheduling and priority queues.

Suggested priorities:
1. Urgent needs.
2. Important world events.
3. Active social interactions.
4. High-priority goals.
5. Routine planning.
6. Memory maintenance.

Initial configurable timing:
- Clock update: approximately once per second.
- Movement: approximately every 250–500 ms while actively rendering.
- Needs evaluation: approximately every 10 seconds.
- Decision evaluation: approximately every 5–15 seconds or on meaningful events.
- Memory consolidation: once per game day.

These are starting values, not immutable rules. Avoid unnecessary network requests. Use AI only when meaningful decisions require it.
