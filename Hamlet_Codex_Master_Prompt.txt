# 1. PROJECT VISION

Hamlet is a 2D mobile simulation of a persistent medieval village. Its long-term vision is a village inhabited by autonomous characters whose needs, personalities, goals, memories, and relationships shape village life.

The inhabitants are not ordinary scripted NPCs. Each character has an identity and background, personality and values, needs and preferences, ambitions, goals, plans, memories, relationships, knowledge, beliefs, occupation, and daily routines. They can initiate conversations, react to events, develop ambitions, and change behavior.

The village must evolve over time through friendships, rivalries, businesses, traditions, rumors, economic relationships, community projects, and unexpected social situations.

The player primarily observes and interacts with the simulation rather than directly controlling every character. The world persists between application sessions. AI is a central gameplay system: it drives character scheduling, goal selection, planning, and context-sensitive decisions. The application must degrade gracefully when AI is unavailable, but deterministic fallback behavior is a resilience path, not the intended primary experience.

**Core design principle:** The simulation owns the world. AI owns character decision-making. AI proposes decisions; the simulation validates and executes them. AI must never directly modify authoritative world state.

# 14. AI ACTION RESPONSE FORMAT

All NPC decision requests return structured JSON. Use Kotlin serialization and strict schemas.

Example:

{
  "npc_id": "thomas",
  "decision_type": "goal_action",
  "reasoning_summary": "I need to acquire flour for my household.",
  "goal": {
    "description": "Acquire flour",
    "priority": 75
  },
  "action": {
    "type": "travel_to",
    "target_id": "market",
    "parameters": {}
  },
  "expected_outcome": "Reach the market",
  "memory_candidates": [
    {
      "content": "I need to purchase flour.",
      "importance": 40
    }
  ]
}

Use brief reasoning summaries only. Do not request or store hidden chain-of-thought.

Validate every field before the action reaches the simulation. If JSON is malformed, retry or use fallback behavior. A failed AI response must never corrupt the world.

# 19. OFFLINE AND DEGRADED OPERATION

Reliable behavior during connectivity loss is mandatory, but online AI-driven scheduling and decisions are the primary experience. Offline operation is a degraded mode, not the default design target.

When offline or when the provider is unavailable:
- World clock advances when execution is permitted.
- Existing schedules and plans continue locally where safe.
- Needs change.
- NPCs move using local rules.
- Existing plans continue.
- Local events are generated.
- Do not accumulate a backlog of obsolete per-NPC decisions. Skip, coalesce, or expire requests according to their type and freshness.
- Deterministic fallback decisions handle essential routines and urgent needs; clearly indicate degraded mode.

When the application reopens:
- Calculate elapsed time using persisted timestamps.
- Advance deterministic simulation systems and resolve eligible elapsed-time events using bounded local rules.
- Do not issue a burst of stale AI calls for every missed decision.
- Revalidate queued AI actions.
- Resume active simulation.

Never blindly execute stale queued decisions.

Account for Android lifecycle and battery restrictions. Do not promise continuous background simulation when Android has suspended the application. Use WorkManager for deferred work. Use a foreground service only when appropriate, permitted, and clearly enabled by the user.

# 21. SIMULATION SCHEDULER

Build a central scheduler for simulation events and AI requests. Do not run 12 permanent polling loops. Use event-driven triggers, batching where appropriate, concurrency limits, and priority queues so meaningful character decisions receive AI attention without flooding the provider or blocking the simulation.

AI should contribute to character schedules and adapt them to needs, goals, personality, relationships, and new events. The simulation owns timing, authoritative state, and execution. Keep routine movement and clock updates local; request AI decisions on meaningful triggers rather than on every frame or tick. Make the cadence configurable and account for provider latency, rate limits, and usage cost.

Suggested priorities:
1. Urgent needs.
2. Important world events.
3. Active social interactions.
4. High-priority goals.
5. Routine planning.
6. Memory maintenance.

Initial configurable timing:
- Clock update: approximately once per second.
- Movement: approximately every 250–500 ms while actively rendering.
- Needs evaluation: approximately every 10 seconds.
- Decision evaluation: approximately every 5–15 seconds or on meaningful events.
- Memory consolidation: once per game day.

These are starting values, not immutable rules. Avoid unnecessary network requests, but do not starve active NPCs of decisions. Use AI when meaningful scheduling or decision events occur, subject to priority, concurrency, and cost controls.
