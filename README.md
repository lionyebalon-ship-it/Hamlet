# Hamlet

Hamlet is an Android-targeted medieval village simulation centered on AI-driven
NPC schedules, goals, and decisions. The simulation remains authoritative:
provider responses are validated proposals, never direct world mutations.

[Project status, work log, and prioritized roadmap](./docs/PROJECT_STATUS.md)

## Current implementation

The app now has a native Compose shell and a Kotlin simulation core:

- Deterministic initialization of The First Hamlet, its 12 villagers, 10
  locations, and directed initial relationships.
- A typed AI decision-provider boundary and per-villager decision context.
- Validation of AI-proposed actions before applying them to world state.
- A deterministic degraded-mode action when the provider is unavailable.
- A village overview rendered from an editable Tiled map and pixel-art tileset,
  with drag panning, pinch zoom, tap-to-select villager sprites, a clear
  selected-villager highlight, simulation clock controls, ambitions, traits,
  and an explicit disconnected AI status.
- A plan-request interaction that runs through the decision service and clearly
  reports when it used local fallback behavior.
- JVM tests and Compose instrumentation tests.

Persistent storage, live Kilo connectivity, pathfinding, and long-term
simulation systems are not implemented yet. The map renderer is native Compose:
it loads the fixed Tiled TMX map and PNG tileset, pre-renders the terrain, then
draws placed building, tree, and villager sprites with nearest-neighbor
filtering. NPC pathfinding, building entry, and interior maps are not
connected to autonomous NPC movement yet. Tapping a building opens its authored
interior; use the in-map return control to go back outside.

## Pixel-art map workflow

The fixed outdoor map is 64 x 40 tiles (1024 x 640 map pixels) in
`src/main/assets/maps/hamlet.tmx`; its original 16 x 16 pixel terrain atlas is
`src/main/assets/tilesets/hamlet.png`. The map is a premade authored layout,
not regenerated for each playthrough. It places small cottages and workshops
around a shared green, with a working farm, kitchen gardens, footpaths, stream,
and woodland at the edges. Open the TMX file in
[Tiled](https://www.mapeditor.org/) to edit terrain, paths, decorations, and
object positions. Keep the existing layer names/types and the embedded
single-image tileset; the Android loader currently supports finite orthogonal
maps with CSV tile layers. In the app, drag with one finger to pan, pinch with
two fingers to zoom, and use the on-map Reset button to restore the starting view.

The PNG tileset is generated by a Go standard-library script:

```sh
go run scripts/generate_hamlet_tileset.go
```

`scripts/generate_hamlet_map.go` can restore the same fixed starter layout; it
refuses to overwrite a map unless `-replace` is supplied. It writes the same
fixed coordinates and terrain every time—there is no runtime map generation.
Continue editing the TMX in Tiled after restoration. The installed Tiled CLI
can check the map without opening a GUI:

```sh
QT_QPA_PLATFORM=offscreen tiled --quit src/main/assets/maps/hamlet.tmx
```

Nine fixed, editable interiors are in `src/main/assets/maps/interiors/`.
They have different footprints (9 x 7 to 12 x 9 tiles), floors, wall types,
and furnishing layouts: the cottages have beds and hearths, the weaver has a
loom and spinning wheel, the smithy has a forge and anvil, the bakehouse has an
oven and flour sacks, the chapel has an altar and pews, and the tavern, farm,
carpenter, and market each have their own practical fittings. Their small
footprints and varied materials are an intentional departure from the former
uniform, oversized plank rooms.

The layouts use a documented historic English hall-house reference as broad
inspiration, not as a claim that every medieval home looked alike:
[Hall house](https://en.wikipedia.org/wiki/Hall_house). Its account describes
timber-framed houses with clay or wattle-and-daub infill, communal hall use, and
open hearths; status, period, and region varied. The maps reflect that variety
with earth, rush, board, brick, and stone floors, and hearths placed according
to each building's purpose.

Every interior records a doorway entry tile. The renderer derives blocked
tiles from wall and furnishing layers, and `TilePathfinder` returns
four-direction tile routes through the remaining floor. JVM tests verify that
the doorway is walkable and every walkable tile in each room is reachable from
it. This provides NPC navigation with real collision-aware paths rather than
assuming the whole room is open floor.

The original `src/main/assets/tilesets/hamlet-interiors.png` atlas contains
the floors, timber/plaster walls, doors, windows, beds, tables, stools,
shelves, hearths, workbenches, counters, ovens, looms, sacks, pottery, baskets,
and other room-specific fittings. Building objects in the outdoor TMX identify
their interior map with an `interior-map` custom property. Restore the authored
maps and furniture atlas with:

```sh
go run scripts/generate_hamlet_interiors.go -replace
go run scripts/generate_hamlet_interior_tileset.go
```

The Android renderer reads the same TMX file and tileset used in Tiled, so map
edits are visible after rebuilding the app; no export step is needed.

## Build and test

Requires a JDK 17 or newer and the Android SDK. The checked-in Gradle wrapper
uses Gradle 9.5.1:

```sh
./gradlew testDebugUnitTest assembleDebug
```

Tests use a fake AI provider; they do not need credentials or network access.
Live provider checks should be run separately only after the Kilo adapter is
implemented and credentials are configured securely.

## Android emulator in this Codespace

The current Codespace has a verified headless Pixel 8 AVD:

- Android Emulator 37.2.13.0
- Android 16 / API 36.1 Google APIs x86_64 image
- 1080 x 2400 display at 420 dpi
- SDK installed at `$HOME/Android/Sdk`
- AVD name: `HamletPixel8`
- AVD configured with 4 GiB RAM and 4 virtual CPU cores

The emulator also needs the Ubuntu runtime libraries `libdrm2` and
`libxkbfile1`:

```sh
sudo apt-get update
sudo apt-get install -y libdrm2 libxkbfile1
```

KVM is available to the container but the device is group-restricted. Launch
the emulator with the device's numeric group added only to that process; this
avoids changing `/dev/kvm` permissions:

```sh
export ANDROID_HOME="$HOME/Android/Sdk"
export ANDROID_SDK_ROOT="$ANDROID_HOME"
sudo setpriv \
  --reuid="$(id -u)" \
  --regid="$(id -g)" \
  --groups="$(stat -c '%g' /dev/kvm)" \
  -- env \
    HOME="$HOME" \
    ANDROID_HOME="$ANDROID_HOME" \
    ANDROID_SDK_ROOT="$ANDROID_SDK_ROOT" \
    ANDROID_AVD_HOME="$HOME/.android/avd" \
    "$ANDROID_HOME/emulator/emulator" \
      -avd HamletPixel8 \
      -no-window -no-audio -gpu swiftshader \
      -no-snapshot -no-boot-anim -memory 4096 -cores 4
```

In another terminal, wait for Android and capture the screen:

```sh
export ANDROID_HOME="$HOME/Android/Sdk"
export PATH="$ANDROID_HOME/platform-tools:$PATH"
adb wait-for-device
adb shell getprop sys.boot_completed
adb exec-out screencap -p > /tmp/hamlet-screen.png
```

For manual iteration, build the debug APK with Gradle, install it with
`adb install -r`, launch its activity, and capture screenshots with adb.
`bash scripts/verify-on-emulator.sh` starts the configured AVD, runs the
Compose instrumentation tests, and captures the app at
`/tmp/hamlet-current-screen.png`. This workflow has been verified in the
upgraded Codespace: both Compose instrumentation tests pass, Hamlet launches,
and the app screenshot is captured.

The Codespace is remote and has no Android Studio GUI. Android Studio's Compose
Preview is therefore unavailable here; use emulator screenshots for visual
iteration, or open the project in Android Studio on a local machine for
interactive Compose previews. See the official
[emulator acceleration guide](https://developer.android.com/studio/run/emulator-acceleration),
[Android SDK CLI reference](https://developer.android.com/tools/agents/android-cli/commands/sdk),
and [Compose Preview guide](https://developer.android.com/develop/ui/compose/tooling/previews).
